# OES-001: Opportunity Engine Standard

## 1. Purpose
The Opportunity Engine is the core of iPhande. It establishes the canonical standard for managing an Opportunity as a long-lived Aggregate Root, progressing through a strict lifecycle from inception to archival.

This standard dictates the architectural boundaries, business invariants, and UI/API interactions to ensure all capabilities—leads, quotes, invoices, work execution, and reflections—build predictably upon the Opportunity.

## 2. Aggregate Root

An Opportunity is not a simple flat object; it is an aggregate constructed from bounded contexts:

```
Opportunity
├── Identity (ID, Slug, Title, Description)
├── Lifecycle (State, Progression Timeline)
├── Visibility (Public, Private, Searchable)
├── Pricing (Estimated Value, Currency, Type)
├── Capacity (Available Slots, Waitlist)
├── Fulfilment (Location, Remote, Requirements)
├── Media (Cover Image, Gallery)
├── Analytics (Views, Clicks, Conversion Rate)
├── Audit (Modification History, Authors)
└── Replay (Append-only Event Sourcing Ledger)
```

## 3. Invariants
Every Opportunity must obey the following business rules:
- **Ownership:** An Opportunity always belongs to exactly one `Business`.
- **Authorization:** Only the owning Business (and authorized users via permissions) can issue commands to mutate it.
- **Immutability:** Archived Opportunities are strictly immutable.
- **Visibility Restrictions:** `Draft` Opportunities are never publicly discoverable.
- **Completeness Constraints:** `Published` Opportunities must satisfy minimum completeness requirements (e.g., must have a title, pricing, and category).
- **History:** Replay history is append-only.
- **Auditing:** Every lifecycle transition must be auditable and linked to a user/steward action.

## 4. Lifecycle State Machine
Opportunities flow through an explicitly defined state machine. Not all transitions are legal.

```
Draft
  ↓
Published
  ↓
Visible
  ↓
Receiving Leads
  ↓
Quoted
  ↓
Accepted
  ↓
Scheduled
  ↓
In Progress
  ↓
Completed
  ↓
Reflected
  ↓
Archived
```

## 5. Commands (Mutations)
The UI issues Commands instead of generic CRUD operations.

- `createOpportunity()`
- `updateOverview()`
- `updatePricing()`
- `updateMedia()`
- `publish()`
- `pause()`
- `close()`
- `archive()`
- `duplicate()`
- `restore()`

## 6. Events
Commands result in domain events recorded in the Replay ledger.
- `OpportunityCreated`
- `OpportunityPublished`
- `OpportunityPriceUpdated`
- `LeadReceived`
- `QuoteAccepted`
- `WorkCompleted`

## 7. Read Models / Projections
The UI consumes ViewModels explicitly designed for the context:
- `OpportunityCardViewModel`
- `OpportunityDetailViewModel`
- `OpportunityAnalyticsViewModel`

Raw DTOs are mapped through adapters in `mappers/opportunityMapper.ts`.

## 8. Query Hierarchy (React Query)
Queries are strictly normalized around aggregates:
- `["opportunities"]` (Base)
- `["opportunities", "feed"]` (Public Discovery)
- `["opportunities", "featured"]` (Public Discovery)
- `["opportunities", "search", filters]` (Public Discovery)
- `["opportunities", "business", businessId]` (Steward Management)
- `["opportunities", "detail", slug]` (Shared View)
- `["opportunities", "analytics", slug]` (Steward Management)
- `["opportunities", "dashboard"]` (Dashboard Projection)

## 9. Frontend Integration
The frontend is split into two products utilizing the same aggregate:
- `management/` -> `app/(steward)/opportunities`
- `discovery/` -> `/opportunities` (Public marketplace)

React Query commands automatically invalidate the specific aggregate keys without over-fetching.

## 10. Backend Integration
The UI maintains a thin API boundary: `api/opportunityApi.ts`.
**No DTOs or mocked logic are fabricated.** The API layer remains a waiting shell until the backend explicitly exports the OpenAPI specification, at which point Orval handles client generation.
