# DIS-001: Dashboard Integration Standard

**Status:** Active  
**Layer:** Platform Projection  

## Background
The dashboard is the central orchestration screen for a user's session. Historically, this screen was responsible for independently discovering, fetching, and aggregating data across multiple disconnected endpoints (leads, opportunities, continuity events). This approach resulted in race conditions, waterfall loading, scattered UI states, and duplicated authorization logic.

## Doctrine
The dashboard is a **Projection**, not a Source of Truth. 

It does not decide what the user can see, it simply renders the pre-computed summary provided by the Platform Kernel.

## Standard Rules

### Rule 1: The Dashboard is a Projection
The frontend dashboard must never perform independent data orchestration. It consumes a single, unified view of the world computed by the backend.

### Rule 2: Single Live Endpoint
The dashboard makes exactly **one** API request for live data:
```http
GET /api/v1/dashboard
```
No other domain endpoints (e.g., `/leads`, `/opportunities`) may be called from the dashboard screen for summary data.

### Rule 3: Bootstrap Snapshot Fallback
The `useDashboardQuery` must initialize using the dashboard snapshot embedded within the `["bootstrap"]` query cache payload. The live `GET /api/v1/dashboard` call should occur seamlessly in the background. If the live endpoint fails (e.g., 404, offline), the dashboard gracefully degrades to the bootstrap snapshot without presenting an error overlay.

### Rule 4: Typed View Models
Components must never consume raw API Data Transfer Objects (DTOs). The Dashboard Mapper translates the API response into strict View Models (`DashboardViewModel`, `TrustCardState`, `WalletCardState`) specifically shaped for the UI.

### Rule 5: Standardized Widget States
Every dashboard widget must explicitly declare its status using the universal `WidgetState` enumeration:
```typescript
export type WidgetState = "snapshot" | "live" | "refreshing" | "unavailable" | "maintenance";
```
Every widget accepts exactly:
```typescript
export interface WidgetProps<T> {
    state: WidgetState;
    data: T | null;
    lastUpdated: string | null;
    error: string | null;
}
```

### Rule 6: Independent Degradation
Widgets SHALL degrade independently. If the backend fails to supply `notifications` data, the Notification Widget renders an `unavailable` state, but the Trust and Wallet Widgets continue rendering their data without issue. One failed domain must not collapse the entire projection.

### Rule 7: Immutability
Projection is immutable. Widgets cannot directly alter dashboard state. All mutations (e.g., accepting a lead) must interact with their respective backend domains and invalidate the `["dashboard"]` and `["bootstrap"]` query keys, forcing React Query to pull a fresh projection.

```text
Mutation -> Backend -> Invalidate Query -> GET /dashboard -> Projection Updates
```
