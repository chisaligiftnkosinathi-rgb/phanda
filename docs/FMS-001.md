# FMS-001: Feature Module Standard

**Status:** Active  
**Layer:** Platform Architecture  

## Background
As the application expands to support multiple interdependent verticals (Marketplace, Finance, Continuity, Opportunities), placing all components in global `src/components` and all hooks in `src/hooks` leads to architectural collapse. FMS-001 enforces Domain-Driven Design (DDD) by grouping related code by feature rather than by technical type.

## Doctrine
A **Feature** is an isolated vertical slice of business capability. 

Features are self-contained. They own their internal state, their API contracts, their data mappers, and their specific presentation components. Features communicate with the Platform Kernel via the `useSession()` hook, but they do not mutate platform state directly.

## Standard Structure

Every feature module MUST reside in `src/features/<feature_name>/` and follow this canonical layout:

```text
src/features/marketplace/
    api/              # React Query hooks and Axios transport calls for this domain
    hooks/            # UI logic, state orchestration, or domain-specific React hooks
    types/            # Domain models, view models, and API interfaces
    mappers/          # Functions converting API DTOs into typed View Models
    components/       # React Native components strictly belonging to this feature
    index.ts          # Public barrel export of components and hooks the rest of the app can consume
```

### 1. `api/`
Contains the transport layer. This is the **only** place where `axios` or `fetchWithAuth` may be imported for this domain. It exposes React Query hooks (e.g., `useMarketplaceQuery`, `useCreateListingMutation`).

### 2. `hooks/`
Contains complex UI or orchestration logic that shouldn't clutter components. 

### 3. `types/`
Contains interfaces describing the domain. It must clearly separate the API payload DTOs from the frontend `ViewModel` structures if they differ.

### 4. `mappers/`
Contains pure functions mapping the raw `types` returned by `api/` into the exact `ViewModel` types required by `components/`. This isolates components from backend contract changes.

### 5. `components/`
Contains presentation components. Components MUST NEVER import `axios` or manually execute data fetches. They receive data through props (View Models) or by invoking hooks from `api/`.

### 6. `index.ts`
The barrel file. It enforces the public interface of the feature. Other modules should only import from `src/features/marketplace` (the barrel), never deep-linking into `src/features/marketplace/components/InternalCard.tsx`.
